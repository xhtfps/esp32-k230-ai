## 一、项目一句话介绍

本项目面向舞蹈机器人表演赛，构建了一个以 ESP32-S3 为比赛主控的多模态自主表演系统。系统将语音、视觉和音乐三类输入统一纳入比赛状态机，由 ESP32 完成识别结果确认、动作指令下发、执行完成反馈和异常恢复，使机器人能够在无人工遥控的条件下完成规定动作和自选动作表演。

答辩时建议使用下面这句话作为开场：

> 我们的核心设计不是把三个识别模块简单拼接，而是用一个带有阶段约束、动作确认和故障恢复的自主执行闭环，把“听懂、看懂、听出节奏”统一转换为可验证、可追踪、可重试的机器人动作。

## 二、比赛要求与项目对应关系

根据规则，比赛在 1.5 m × 1.5 m 表演区域内进行，机器人需在 15 分钟内自主完成三个部分：

| 比赛环节 | 规则要求 | 项目对应实现 | 当前证据 |
|---|---|---|---|
| 语音识别-动作表演 | 规定 3 个语音-动作 + 3 个自选语音-动作；识别成功和动作完成分别计分 | SU-03T 接收语音动作编号，ESP32 映射为 Arduino 动作字节并等待 ACK | `main.c`、`arduino_command_map.c`、`READ.txt` |
| 视觉识别-动作表演 | 规定 2 个视觉-动作 + 2 个自选视觉-动作；识别与动作均计分 | PC 端姿态识别或 ESP32 本地姿态识别，稳定结果经统一编号发送给 ESP32 | `eyes/pc_pose/main.py`、`POSE`、`WEB`、`main.c` |
| 音乐韵律识别-动作表演 | 规定音乐须先识别，再完成 60-90 秒表演；随后完成 90-120 秒自选音乐表演 | INMP441 采样、特征/指纹匹配、置信度与差异度判定，再选择官方舞蹈或自选舞蹈 | `music_recognizer.c`、`competition_controller.c` |
| 技术陈述 | 表演后约 1 分钟陈述技术创新点，附加分满分 5 分 | 本文提供 1 分钟陈述稿和技术问答 | 本文第五、六节 |

规则中的重要限制：比赛总过程 15 分钟，三个环节各不超过 5 分钟；机器人启动后须自主运行，禁止使用遥控器、手机等通信设备控制机器人；动作应在场地内完成，越界、触碰和故障处理可能产生扣分。

```text
                 └──────────┬───────────┘
                            │
       ┌────────────────────┼────────────────────┐
       │                    │                    │
       ▼                    ▼                    ▼
  SU-03T 语音          摄像头视觉             INMP441 音频
       │          PC 模式 / ESP32 本地模式       │
       └────────────────┬───────────────────────┘
                        ▼
                ┌─────────────────┐
                │    ESP32-S3      │
                │ 比赛状态机/判定  │
                │ 指令映射/超时    │
                └───────┬─────────┘
                        │ UART2
                        ▼
                ┌─────────────────┐
                │ Arduino 动作桥接 │
                └───────┬─────────┘
                        │ 蓝牙/机器人控制链路
                        ▼
                ┌─────────────────┐
                │ STM32 + 执行机构 │
                └───────┬─────────┘
                        │ 动作完成 ACK
                        └──────────────► ESP32 状态机
```

### 3.1 硬件与通信链路

- SU-03T 通过 ESP32 UART1 接入，当前文档记录为 GPIO1/GPIO2、115200、8N1。
- Arduino 通过 ESP32 UART2 接入，当前文档记录为 GPIO20/GPIO21、115200、8N1。
- ESP32 向 Arduino 发送单字节动作指令，不追加 CR/LF；Arduino 完成动作后回传对应字节作为 ACK，错误字节为 `0xFE`。
- ESP32 还可向 SU-03T 发送五字节播报帧 `AA 55 <message_id> 55 AA`，用于播报视觉识别结果和音乐编号。
- PC 视觉模式通过 Wi-Fi 读取 ESP32 摄像头 MJPEG 流，并向 `/api/vision/pose` 提交稳定姿态结果。

## 四、三个比赛环节的技术实现

### 4.1 语音识别-动作表演

比赛流程：

1. SU-03T 发送 `0xAA`，ESP32 进入语音环节。
2. SU-03T 输出动作编号 1-8。
3. ESP32 根据统一映射表将语音编号转换为 Arduino 动作字节。
4. ESP32 锁定当前动作，等待 Arduino 返回同一字节 ACK。
5. ACK 正确时动作计数增加；收到 `0xFE` 或 20 秒未收到 ACK 时，动作失败并恢复识别状态。

| 语音编号 | 动作 | Arduino 字节 |
|---:|---|---|
| 1 | 前进 | `0x31` |
| 2 | 左脚撑 | `0x33` |
| 3 | 举左手 | `0x32` |
| 4 | 向左转 | `0x34` |
| 5 | 向右转 | `0x39` |
| 6 | 戒备 | `0x61` |
| 7 | 防御 | `0x62` |
| 8 | 出拳 | `0x63` |

答辩重点：语音环节不是“收到字节就立即连发动作”，而是采用“识别接受 - 指令下发 - ACK 确认 - 状态恢复”的闭环，避免动作重入、重复触发和动作尚未完成时收到下一条指令。

### 4.2 视觉识别-动作表演

项目提供两种互斥视觉模式：

- PC/Wi-Fi 模式：电脑运行 Ultralytics 或 MMPose 后端，使用 YOLO11n-Pose 等姿态模型提取人体关键点；`TeamPoseClassifier` 进行动作分类和稳定帧判断；稳定结果经 HTTP POST 发送给 ESP32。
- ESP32 本地模式：OV2640 JPEG → ESP JPEG 解码 → ESP-DL COCO Pose → 17 个关键点 → C 语言几何分类器 → 稳定姿态确认。该模式不依赖电脑和 Wi-Fi，适合在现场网络条件不稳定时作为备用方案。

视觉动作编号如下：

| 视觉消息编号 | 识别动作 | Arduino 字节 |
|---:|---|---|
| 1 | 大字站 | `0x35`（RA） |
| 2 | 举双手 | `0x37`（RB） |
| 3 | 蹲下 | `0x36`（RC） |
| 4 | 弓箭步 | `0x38`（RD） |
| 5 | 叉腰 | `0x42`（L1） |
| 6 | 敬礼 | `0x43`（L2） |

视觉环节的关键保护机制：

- 进入视觉环节后不会自动识别，必须再接收 `0x11` 才会“武装”一次识别。
- 识别成功后立即解除武装，下一次动作必须重新收到 `0x11`，防止同一姿态被连续重复计分。
- PC 和本地模式共用相同的 1-6 视觉消息契约，降低双模式切换时的联调成本。
- 本地推理结果只有在稳定帧判定通过且上一动作没有等待 ACK 时才会下发。

### 4.3 音乐韵律识别-动作表演

音乐环节采用“先识别、后表演”的两阶段流程：

1. SU-03T 发送 `0xCC` 进入音乐环节。
2. SU-03T 发送 `0x22`，ESP32 启动 INMP441 音频采集和识别任务。
3. 系统先丢弃 2500 ms 的提示音/播报保护区，再采集约 16 秒音频。
4. 对音频进行分帧、频带能量分析和指纹提取，使用带偏移搜索的加权投票匹配 5 首官方音乐。
5. 只有同时满足置信度阈值 `0.40` 和候选差异度阈值 `0.08` 才接受识别结果。
6. 识别成功后，`0x55` 触发官方舞蹈，`0x66` 触发自选舞蹈；官方音乐编号 1-5 分别映射到舞蹈指令 `0x66、0x64、0x65、0x41、0x44`，自选舞蹈使用 `0x45`。

该设计的答辩表述：系统不把“最相似”直接当成“识别正确”，而是同时检查匹配强度和第一名与第二名的差异度；识别失败可重新发送 `0x22` 重试，不会把低置信度结果误触发为舞蹈。

## 五、软件设计与创新点

### 5.1 比赛状态机统一管理三类任务

`competition_controller.c` 将比赛建模为多个明确状态，包括准备、识别运行、动作下发、等待动作完成、音乐识别、官方表演、自选表演、完成、超时中止和故障状态。

状态机提供四类比赛级保护：

- 阶段顺序由裁判/语音事件选择，不依赖动作数量；每个阶段只能进入一次。
- 总时限和单阶段时限分别限制为 15 分钟和 5 分钟。
- 识别、动作执行、音乐识别和音乐表演分别有独立的接受条件。
- 失败恢复到可重试状态，避免一次识别失败导致整个比赛流程死锁。

### 5.2 多模态输入使用统一消息契约

语音动作、视觉动作和音乐舞蹈最终都转换为少量稳定的消息编号和 Arduino 单字节指令。这样做的好处是：

- 上层识别算法可以替换，底层动作桥接接口不变。
- PC 视觉和 ESP32 本地视觉使用相同的姿态编号，现场可切换视觉源。
- 动作完成 ACK 只关注“当前动作是否完成”，不需要理解上层识别算法的内部细节。

### 5.3 面向比赛现场的容错设计

- Arduino ACK 超时监测任务每 50 ms 检查一次，超过 20 秒自动结束等待状态。
- 动作错误、ACK 不匹配、重复指令和非法阶段事件均被拒绝或记录日志。
- 音乐识别保留候选、投票、重叠长度、置信度和差异度诊断信息，便于现场快速定位“没有采到音频”“特征不足”或“候选相近”等问题。
- BOOT 按键支持 PC/Wi-Fi 与 ESP32 本地视觉模式切换，并在切换时释放和重新初始化相关摄像头、Wi-Fi 资源。

## 六、建议使用的技术答辩主线

### 6.1 1 分钟创新陈述稿

各位评委好，我们的项目是一套面向舞蹈机器人表演赛的多模态自主表演系统。系统以 ESP32-S3 为主控，将 SU-03T 语音识别、PC 或 ESP32 本地视觉识别、INMP441 音乐识别统一接入比赛状态机。

我们的第一个创新是自主执行闭环：每次识别结果都必须经过阶段校验、动作指令下发和 Arduino ACK 确认，出现错误或超时可以自动恢复，避免动作重复和流程卡死。第二个创新是视觉双模式：正常情况下使用 PC 端姿态识别获得较好的实时性，现场网络或电脑不可用时可以切换到 ESP32-S3 本地姿态识别。第三个创新是音乐识别的可靠性设计：系统先过滤播报提示音，再利用音频指纹、加权投票、置信度和候选差异度联合判定，识别失败可以重试。

因此，我们的重点不是单个算法，而是把三种识别能力组织成一个可验证、可恢复、符合比赛自主运行要求的完整闭环。

### 6.2 3 分钟技术答辩稿

本项目的软件分为输入层、比赛控制层、动作桥接层和执行层。输入层包括 SU-03T、PC/ESP32 视觉和 INMP441；比赛控制层由 `competition_controller` 维护阶段、动作、时间和失败恢复；动作桥接层负责把统一消息编号映射为 Arduino 指令，并等待动作完成反馈；最终由 Arduino、STM32 和机器人执行机构完成动作。

在语音环节，SU-03T 的动作编号通过固定映射表转换为单字节指令。ESP32 不会在动作执行期间继续接受新的动作，而是等待匹配 ACK。视觉环节采用一次武装、一次识别、一次动作完成的节拍，防止稳定姿态被重复提交。音乐环节先采集并识别官方音乐，只有识别成功后才允许开始官方舞蹈；官方舞蹈完成后再进入自选舞蹈，和规则要求的“识别阶段不能跳过”保持一致。

在可靠性方面，系统设置了 15 分钟总时限、5 分钟单环节时限、20 秒动作 ACK 超时和音乐识别重试机制。对于视觉识别，我们同时保留 PC 高精度模式和 ESP32 本地模式，二者输出相同的消息契约。这样既保证正常情况下的识别效果，也为比赛现场的网络和设备异常准备了备用路径。

## 七、评委可能追问与建议回答

### 问题 1：你们如何证明机器人没有被遥控？

建议回答：机器人动作指令由比赛环节内的语音、视觉和音乐事件触发，ESP32 通过状态机限制合法阶段和合法动作，并通过 Arduino ACK 确认动作完成。比赛展示时应同时说明现场使用的设备边界，并移除手机、遥控器和可疑通信设备。当前代码能证明指令来源和状态约束；现场合规性还需要通过实际布置照片或演示视频证明。

### 问题 2：视觉识别误触发怎么办？

建议回答：视觉阶段需要先接收 `0x11` 才允许识别；分类器还要满足稳定帧条件。识别成功后立即解除武装，必须重新发起下一次识别。PC 和本地模式都使用同一套动作编号，识别源切换不会改变动作映射。

### 问题 3：音乐识别为什么不是直接比较音量？

建议回答：音量容易受播放距离、场地反射和环境噪声影响。系统提取频带能量和时间序列指纹，并通过带偏移的加权投票比较候选音乐，同时使用置信度和第一、第二候选差异度做双重门限，降低误识别风险。

### 问题 4：如果 Arduino 没有返回完成信号呢？

建议回答：ESP32 为每个动作设置唯一的等待上下文，接收匹配字节才算完成；收到错误字节或超过 20 秒没有 ACK 时，动作被判定为失败并恢复到识别状态，同时记录日志。这样不会因一个动作卡住而无限等待。

### 问题 5：为什么要保留 PC 和本地两种视觉模式？

建议回答：PC 模式适合实时、高精度视觉识别；本地模式不依赖电脑和 Wi-Fi，适合现场网络不稳定的情况。两种模式最终都输出 1-6 的统一视觉消息，因此切换的是识别来源，不是整套比赛逻辑。

### 问题 6：你们的机械结构和电路创新是什么？

建议回答模板：这部分必须结合实物材料回答。建议从“机械自由度与动作表现”“独立供电和控制单元”“PCB/线束安全与可维护性”“现场拆装和检修”四个方面展开，并用结构图、电路框图、PCB 图和实物照片逐项对应。当前代码目录只能直接证明软件和通信部分，机械参数、自由度数量和 PCB 创新需要补充材料后再作具体表述。

## 九、技术事实与材料边界

### 当前代码可以直接支撑的结论

- ESP32-S3 固件存在比赛状态机、语音映射、视觉映射、音乐识别、动作 ACK 和超时处理。
- PC 端和 ESP32 本地端使用统一的六类姿态消息。
- 音乐识别包含提示音保护区、16 秒采样、音频特征/指纹匹配、置信度和候选差异度判定。
- 项目包含串口、视觉、音乐和比赛控制相关测试契约文件。

### 当前目录不能直接支撑的结论

- 机器人整机尺寸、重量、自由度数量和实际动作幅度。
- 电池容量、峰值电流、PCB 自主设计比例和电气安全测试结果。
- 现场识别准确率、帧率、音乐识别准确率和连续运行成功率。
- 机器人在实际场地内不越界、不摔倒和不触碰的最终效果。

答辩原则：对第一类内容可以直接结合代码讲实现；对第二类内容先补实物证据，再给出定量结论。没有测试数据时使用“设计目标”“当前实现”“待现场验证”三种表述，不要把设计意图说成已经验证的性能。
